# ADR 0014: Scenario-specific point-in-time FX lineage

## Decision

Associate every persisted FX-rate input with the exact landed-cost scenario that uses
it. Preserve the existing bundle-level `fx_rates` input as a shared default, while
allowing each scenario to provide an explicit override collection. Store one row per
scenario and rate identity, with its exact decimal rate and evidence reference.

Define rate identity inside a scenario as base currency, quote currency, rate type,
and effective time. Reject duplicate identities before calculation so conversion does
not depend on input traversal order. Enforce the same invariant in PostgreSQL with null
effective times treated as equal.

Expose a tenant-scoped run endpoint that joins each rate to scenario and source
provenance. Include rate type, effective/retrieval time, evidence class/confidence, and
transformation, but omit raw evidence bodies from the decision-oriented view.
Render the same scenario-linked rate and source metadata in newly generated Persian
reports through the existing untrusted-Markdown escaping boundary.

## Consequences

- Optimistic, base, and conservative scenarios can use different explicit FX inputs
  without losing historical reproducibility.
- Existing bundles continue to work; their shared rates become explicit lineage rows
  for all three scenarios.
- Validation evaluates distinct rate/evidence combinations while avoiding repeated
  penalties when the same evidence-backed rate is shared.
- Migration `20260901_0010` backfills historical shared rates across existing scenario
  rows. Its downgrade must collapse scenario multiplicity because the legacy schema
  cannot represent different values for the same run-level rate identity.
- No live or assumed FX value is generated by this feature; acquisition and evidence
  classification remain separate responsibilities.
